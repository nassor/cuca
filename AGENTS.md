# Repository Guidelines

## Project Overview

CUCA (**Compact Universal Client for Agents**) is a high-performance, asynchronous Rust client library intended to sit between autonomous agent orchestrators and LLM backends: an ultra-low-overhead runtime that monitors, parses, and dispatches multi-modal SSE streams. Tagline: *"Legendary vigilant witch; small footprint that constantly watches for responses."*

Current state: **implemented**. The unified client (`CucaClient`/`CucaClientBuilder`), the zero-allocation SSE parser, eight provider adapters (seven HTTP, one in-process local engine), twelve feature-gated plugins, and seven explicit-call services, including the speculative fast/slow orchestrator, are all implemented.

## Architecture & Data Flow

**Implemented:** the unified client pipeline, the SSE parser, the provider adapters, the plugins, and the services. The architecture:

- **Unified provider abstraction**: one `AgentRequest` in, one normalized `AgentResponseStream` out, across OpenAI, Anthropic, DeepSeek, Gemini, llama.cpp, vLLM, LM Studio, and the in-process local engine (`ProviderEndpoint` enum, `UnifiedMessage`, `MessageContentBlock`). `provider-local` (`src/provider/local/`) runs a GGUF language model in the same process, on the CPU through candle by default, generically like llama.cpp: `general.architecture` selects the behaviour from one table (`model/arch.rs`: `gemma4`, `gemma3`, `llama`, `qwen2`, `qwen3`, `phi3`, `smollm3`, `granite`, `qwen3moe`, `olmoe`, `olmo2`, `ernie4_5`, `muse-glimmer` (sliding-window dense with a separate attention gate, sandwich norms and NoPE global layers), `mistral3` (Llama layers with the YaRN log multiplier and Llama 4 query scaling, CPU and GPU), `mistral4` (multi-head latent attention with a one-row-per-position latent K/V cache, softmax MoE with fused gate/up experts and an ungated shared expert; CPU only), `qwen35` and `qwen35moe` (hybrid delta-net, on the CPU and on a GPU), plus the `gemma4-assistant` MTP drafter), and the loader derives every dimension from the GGUF metadata and tensor shapes (no checkpoint constants), including grouped-query attention, per-layer head counts, sliding-window patterns, LongRoPE and mixture-of-experts layers (`Behavior::moe_norm_weights` says whether the top-k weights are renormalised: not for `olmoe`); an unknown architecture, tokenizer or `tokenizer.ggml.pre` fails loudly naming the value. The tokenizer (`tokenizer/`: SentencePiece `llama`, byte-level BPE `gpt2` with hand-written pre-tokenizers per `tokenizer.ggml.pre`, and the space-escaped `gemma4` scheme) and the chat template (`chat/`: the GGUF's own Jinja text through minijinja) come from the file; `ChatFormat` derives the end-of-generation ids, the reasoning markers and the tool-call syntax from the vocabulary and the template, and `OutputParser` (`output/`) turns generated ids into `Text`, `Thinking` and `ToolCall` blocks. Models are chosen with `ModelSource` (`ModelSource::PRESETS`, the verified preset table with pinned commits and SHA-256, plus `hugging_face`, `File`, or a name via `str::parse`; default `gemma4-e2b-q4_0`); `LocalModelConfig::drafter` (`Option<DrafterSource>`: `File(ModelSource)`, the Gemma 4 MTP drafter, or `InTrunk`, a head inside the main model's own file, CPU only) enables self-speculative decoding. The engine code is pure Rust (no FFI written by cuca), with no HTTP endpoint and no llama.cpp (whose sources were only a design reference). `LocalModelConfig.device` (`LocalDevice`: `Cpu` default, `Vulkan(GpuAdapter)`, `Metal(GpuAdapter)`, `Cuda(usize)`, `Rocm(usize)`; parses from `cpu`, `vulkan[:<n>|:integrated:<n>]`, and so on) moves the forward pass to a GPU through burn 0.22 / CubeCL (`src/provider/local/model/gpu.rs`, same math as the CPU engine, every architecture of the table). Five features select it: `provider-local-gpu` (the shared engine, no backend alone) and `provider-local-vulkan`, `-metal`, `-cuda`, `-rocm`, each enabling `provider-local-gpu` plus the matching `burn` backend. Every `LocalDevice` variant exists in every build; a GPU whose feature is off fails `LocalModel::load` with `CucaError::Config` before any thread starts, and a GPU that cannot be opened fails it with `CucaError::Provider` (the engine thread catches panics during load). On a GPU, Q4_0 and Q8_0 matmul weights stay block-quantized on the device and F32, F16 and BF16 are uploaded as f32; every other dtype (Q4_1, Q5_x, Q8_1, K-quants) is dequantized at load and requantized to Q8_0 (about its file size or less on the device, with a rounding error of at most half a Q8_0 step per element). There is no automatic device selection. `LocalModelConfig::experts` (`ExpertPlacement`: `Resident` default, or `Tiered(ExpertTiers { ram_bytes, device_bytes, loader_threads, warm_from })`, parses from `tiered:ram=4g,device=6g`) keeps a MoE model's routed experts in the GGUF file and loads them on demand (`model/tier.rs`: positional reads by a loader pool, per-layer slot tables sized from byte budgets with a `n_used` minimum, learned heat with halving, a RAM tier on every device plus a device tier of uploaded weights on a GPU); output equals the resident mode's on the same device (bit for bit on the CPU), and `LocalModel::expert_tier_stats` / `expert_heat` expose counters and the exportable heat. `LocalModel::load` downloads (resumable, SHA-256-verified) or opens the file, and `CucaClientBuilder::with_local_model` attaches it for `ProviderEndpoint::Local`.
- **Zero-default provider policy**: no provider compiled by default (`default = []`); a `compile_error!` fires if no provider feature is enabled. Providers are opt-in Cargo features (`provider-openai`, `provider-anthropic`, …).
- **Zero-allocation SSE engine.** `SseStreamParser` is a byte state machine over `bytes::BytesMut`; inbound chunks are scanned with `memchr` in contiguous buffers, with no intermediate string allocation.
- **Plugins and services.** A plugin implements `trait CucaPlugin` (`on_request` / `on_stream_chunk` / `on_response_complete`) and observes the request/stream pipeline; it is compile-time feature-gated and carries its own non-core dependencies. A service is an explicit-call, client-level capability driven by direct method calls instead of pipeline hooks; a service MUST NEVER implement `CucaPlugin`, so registering one with `register_plugin` is a compile error rather than an inert no-op.
- **Fast/slow orchestration** (`service-speculative`): `ModelOrchestrator` + `SwappableModelPair`; complexity routing → speculative draft generation → fallback cascades on malformed output.

Data flow: builder selects provider → `UnifiedRequest` passes through registered plugins (`on_request`) → provider adapter translates to vendor protocol → SSE stream parsed into `MessageContentBlock` events → each chunk passes plugins (`on_stream_chunk`) → `on_response_complete`.

## Code Conventions & Common Patterns

Follow Rust defaults plus the conventions below:

- **Naming**: snake_case functions/variables, CamelCase types (`CucaClient`, `CucaPlugin`, `UnifiedRequest`, `MessageContentBlock`); plugin names are `&'static str` (e.g. `"opentelemetry-observability"`).
- **Error handling**: `CucaError` + `PluginError`; plugins return `Result<(), PluginError>`, client methods `Result<AgentResponseStream, CucaError>`. Avoid `unwrap`/`panic` in library code.
- **Async:** provider and async plugins use Tokio; the public stream contract is `futures_core::Stream` and yields `Result<MessageContentBlock, CucaError>`.
- **Feature gating:** `default = []`; `lib.rs` requires at least one `provider-*` feature. Provider, plugin, and service code MUST be `#[cfg(feature = "…")]`-gated, and each non-core dependency MUST be enabled only by its owning feature via `dep:`. Cross-tier feature and code edges additionally obey *Plugins and services* below.
- **Dependency injection**: providers via builder (`CucaClient::builder().with_provider(…).register_plugin(Arc<dyn CucaPlugin>)`); plugins as `Arc<dyn CucaPlugin>` (Send + Sync).
- **State management**: session state is append-only trajectory logs with fork support (`SessionStorePlugin`); no global mutable state.
- **Memory**: state that grows with traffic is capped, evicting or offloading at the bound; see *Memory discipline* below.
- **Data modeling**: `#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]` on all wire types.

### Plugins and services (no cycles)

Core, plugins and services form a DAG at three levels: Cargo features, `#[cfg]`/import edges, and runtime coupling. Cargo rejects feature cycles; the code and runtime levels are on contributors.

**Tiers.** Core (`types`, `request`, `error`, `sse`, `session`, `plugin`, `client`, `provider`, `export`, `canonical`, `tokenize`, `cost_otel`) sits below every plugin and every service. The plugin tier is flat: `memory`, `session-log`, `mcp`, `sandbox`, `guardrails`, `subagent`, `hitl`, `web-search`, `skills`, `telemetry`, `cost`, and `redaction` depend on core only, and no plugin depends on another plugin. Services depend on core and on the plugin features they declare: `entity-extraction → memory` (hard, `service-entity-extraction = ["plugin-memory"]`), `replay → session-log` (hard, `service-replay = ["plugin-session-log"]`), `vector-store → memory` (hard, `service-vector-store = ["plugin-memory", "dep:wide"]`), and `speculative → session-log` (documented-optional: `ModelOrchestrator::with_session_store` records `SessionEvent::ModelSwap`); `prompt-cache`, `rate-limit` and `scheduler` declare no plugin dependency at all.

- **Direction is one-way:** a plugin MUST NOT name a service in any form: no `use crate::services::<name>`, no `cfg(feature = "service-<name>")` (including inside `cfg(all(…))`), no runtime lookup. `src/plugins/` stays ignorant that any service exists. A service→service edge requires re-tiering the shared part downward first.
- **Declare every code edge:** any compile-time reference from a service to a plugin it uses REQUIRES `service-<name> = ["plugin-<other>", …]` in `Cargo.toml`; never rely on a peer being co-enabled by accident.
- **Coordinate in core, never downward:** core MAY `#[cfg]`-reference any plugin or service; neither MUST reach a peer through a core module to dodge the two rules above. Multi-capability workflows live in core: `CucaExport::from_live` in `src/export.rs`, and `OtelCostObserver` in `src/cost_otel.rs`, the cost-ledger-to-OpenTelemetry bridge gated `cfg(all(feature = "plugin-cost", feature = "plugin-telemetry"))`.
- **No runtime peer discovery:** plugins and services MUST NOT look each other up. `CucaClient::plugins()` is an inspection accessor, not a service locator: no name matching, no downcasting. Cross-tier data moves through a caller-injected `Arc<dyn Trait>` or an explicit application hand-off (`EntityExtractionReport.delta` → `MemoryPlugin::merge_graph`).
- **Optional cross-tier behavior is documented and loud:** behavior that exists only when a declared peer is co-enabled or a peer handle is attached MUST be named in the owning module's `//!` docs, listed in the tiers above, and degrade loudly: compile-gated out of existence (`ModelOrchestrator::with_session_store`) or an explicit error (`CucaExportError::Unsupported` for a compiled-out export section). Silently doing nothing is a defect.
- **No hidden hook-order dependence:** `on_request` hooks run in registration order over one shared `UnifiedRequest`; a plugin MUST NOT require a position relative to another plugin. Where order is observable, document it at the consuming site: memory's graph/warning injections change the digest `PromptCache::lookup` computes afterward.
- **Explicit-call services:** a service is driven by direct method calls rather than pipeline hooks and MUST NOT implement `CucaPlugin` (`PromptCache`, `EntityExtractor`, `SessionReplay`, `ModelOrchestrator`, `RateLimiter`, `InMemoryVectorStore`, `Dispatcher`), so registering one is a compile error instead of an inert no-op; its `//!` header names the real entry points and any mandatory hand-off.

**Checks.** Every plugin or service feature MUST build alone on one provider (`cargo check --all-targets --no-default-features --features provider-openai,plugin-<name>` or `…,service-<name>`); CI runs that matrix across two jobs, `plugin_solo` and `service_solo`, which is how undeclared and reverse code edges are caught: `--all-features` cannot catch them. CI also greps every plugin directory for `service-` feature names, `crate::services` paths, and the `plugins::` paths the five moved modules left behind, since a `cfg(all(…))` reverse edge compiles in both the solo and all-features builds.

### Memory discipline (bounded by default)

Memory size is a first-order concern: every structure that grows with traffic ships bounded, with a stated policy at the bound.

- **Compact structures first.** Keep stream bytes in one reusable `BytesMut` scanned with `memchr` (`SseStreamParser`); pre-size known growth (`MemoryGraph::with_capacity`/`reserve`) instead of reallocating.
- **Cap every growable collection.** A new cache, log, buffer, or map that outlives one request REQUIRES a validated bound at construction, in the mold of `PromptCacheConfig::new` (rejects zero capacity), `MemoryConfig` (`max_messages`/`max_tokens`/`max_fraction`), `GraphContextConfig` (`max_nodes`/`max_relationships`), and `SandboxConfig::max_memory_bytes`. An uncapped collection is a defect unless its docs state why growth is bounded elsewhere.
- **Evict or offload at the cap.** State the at-cap policy in the owning type's docs and reuse an existing shape: TTL plus deterministic LRU eviction (`PromptCache`, `lru_order`), the ordered `CompactionStrategy` pipeline (`Offload` to a caller-supplied `VectorStore`, `Summarize`, `ClampOversizedMessages`, `SlidingWindow`), or append-only offload to disk (`SessionLogPlugin` with `FileBackend`). Unbounded growth is a defect; so is silent data loss.
- **Expose usage and warn near the cap.** A capped structure surfaces a cheap usage reading. Follow memory's seams: `ContextUsageObserver` receives a `ContextUsage` on every request (the reporting gauge), and `MemoryConfig::warn_fraction` injects a one-shot near-limit warning (idempotent via marker scan). Alerting and export belong on the caller-supplied OTel meter (`OpenTelemetryPlugin`); never install a global provider.
- **Re-verify bounds when touching hot paths.** A change to the SSE engine, compaction, a cache, or the graph MUST keep the owning module's `//!` allocation and bounds story accurate (`src/sse.rs` documents its per-frame allocations; `src/plugins/memory/graph.rs` documents its complexity envelope).

## Runtime/Tooling Preferences

- **Rust 1.98.0**, pinned by the root `rust-toolchain.toml` (`channel = "1.98.0"`, `profile = "minimal"`, components `clippy` + `rustfmt`); MSRV `rust-version = "1.98"` in package metadata.
- **Cargo** is the only build/package tool; no alternative package managers.
- **Crate CI**: `.github/workflows/ci.yml` runs nine jobs: `fmt`, `clippy` and `test` (each over the `provider-openai`-only and `ALL_NO_LLVM` points), `doc` (also `ALL_NO_LLVM`), `no_provider` (asserts the bare build fails), `local_gpu_llvm` (ubuntu; `cargo check --all-targets --no-default-features --features provider-local-cuda,provider-local-rocm`, the only job that downloads the prebuilt LLVM bundle), `plugin_solo` (per-plugin solo build, one matrix leg per plugin feature), `service_solo` (the same, one matrix leg per service feature), and `plugin_layering` (flat-tier greps; see *Plugins and services*). `ALL_NO_LLVM` is a top-level `env` list of every feature except `provider-local-cuda` and `provider-local-rocm` (the docs.rs feature set), expanded by the run step's shell as `--no-default-features --features $ALL_NO_LLVM`. The `test` job sets `CARGO_PROFILE_DEV_DEBUG: 0`: each of the 73 test, example and lib-test binaries of the `ALL_NO_LLVM` build links burn, wgpu, wasmtime and candle, 0.7 to 2 GB apiece with debug info, which fills the runner's disk (rust-lld then dies with SIGBUS); without debug info the whole target is 12 GB (measured in a Linux container). Clippy enforces `-D warnings` with `--all-targets`. No rustfmt/clippy config files; defaults apply.
- **Docs CI**: `.github/workflows/docs.yml` runs two jobs, triggered by a push to `main` or a pull request touching `docs/**` or the workflow itself, plus `workflow_dispatch`. `build` installs Zola 0.23.4 from the pinned `getzola/zola` release tarball, verifies its SHA-256, then runs `zola build`, `zola check`, and `python3 search-index.py public` in `docs/`, and uploads `docs/public` as the Pages artifact; `zola check` is the gate on broken `@/` links. `deploy` is gated on `github.event_name != 'pull_request' && github.ref == 'refs/heads/main'`, so a pull request builds and link-checks without deploying, and a `workflow_dispatch` on `main` republishes the committed site without a new commit. Workflow permissions are `contents: read`; `deploy` alone adds `pages: write` and `id-token: write`. The concurrency group is `pages` with `cancel-in-progress: false`. The repository Pages source MUST be set to GitHub Actions, not a branch, or `deploy` fails.
- **Dependencies:** core `bytes`, `futures-core`, `memchr`, `serde`, and `serde_json`; feature-gated `reqwest`, `tokio`, `tokio-stream`, `rmcp`, `wasmtime`, `tiktoken-rs`, `jsonschema`, OpenTelemetry, `tracing`, `sha2`, `getrandom`, `base64`, `postcard`, and `wide`. `provider-local` adds `unicode-general-category` (the BPE pre-tokenizers; pure Rust), `candle-core` and `candle-nn` (0.11; candle-core hard-depends on `tokenizers[onig]`, so the tree compiles C through `onig_sys`, which needs a C compiler; `esaxx-rs` is also in the tree but its C++ `cpp` feature is off, so it builds as pure Rust; cuca does not use `tokenizers` itself), `half`, `minijinja`, and `minijinja-contrib`, and reuses `reqwest` (model download), `sha2` (checksum) and `tokio`; it does not use `tokio-stream`. `provider-local-gpu` adds `burn` 0.22 (`default-features = false`, features `std`, `fusion`, `autotune`, `extension`, `cubecl`; burn's defaults enable optim and autodiff, which inference never uses) over CubeCL, plus `burn-cubecl` 0.22 and `cubecl` 0.11 directly for the MoE kernels (`model/moe_kernel.rs`: `#[cube(launch)]` kernels launched through the checked `launch`, attached with burn's `backend_extension`). Every GPU feature compiles C: CubeCL's runtime (`cubecl-runtime` feature `std`, unavoidable) pulls an embedded store, `turso`/`turso_core`, that builds C through `cc` (`simsimd`, `aegis`), and on Windows its dependency `turso_sdk_kit` runs the Windows SDK resource compiler (`rc.exe`; `windres` on the GNU target) in a build script. That needs a C compiler, which `provider-local` already requires for `onig_sys`, plus the SDK resource compiler on Windows. The graphics backends themselves are Rust (wgpu: SPIR-V for `provider-local-vulkan`, MSL for `provider-local-metal`; Metal runs on Apple only but compiles everywhere). `provider-local-cuda` and `provider-local-rocm` additionally pull cubecl's LLVM backend, whose `tracel-llvm-bundler` build script downloads a prebuilt LLVM on the first build (network needed once, cached) and links it statically, and ROCm (HIP bindings) is Linux-only. The GPU drivers are system libraries loaded at runtime (the Vulkan loader through wgpu/ash). Test-only Tokio and `tokio-stream` support the crate's test suite, and `divan` is the bench-only harness.

## Testing & QA

- **Unit tests**: `#[cfg(test)]` modules next to the code, one per feature module, gated with the same feature flags. Plain `#[test]` plus `#[tokio::test]` (current-thread flavor only; `rt-multi-thread` is not a declared tokio feature of this crate).
- **Integration suite**: `tests/` holds one file per plugin (`plugin_mcp.rs`, `plugin_subagent.rs`, `plugin_hitl.rs`, `plugin_web_search.rs`, `plugin_cost.rs`, `plugin_redaction.rs`, plus the memory/guardrails/telemetry/session-log/skills/sandbox files) and one file per service (`service_prompt_cache.rs`, `service_entity_extraction.rs`, `service_replay.rs`, `service_speculative.rs`, `service_rate_limit.rs`, `service_vector_store.rs`, `service_scheduler.rs`), `plugin_combinations.rs` for cross-tier combinations, and `public_exports.rs`, sharing the harness in `tests/common/mod.rs`. Each single-feature file compiles only when `provider-llamacpp` and its own feature are on, via a top-level `#![cfg]` gate; `plugin_combinations.rs` instead gates each combination module with its own per-module `cfg(all(feature = "…", feature = "…"))`; `public_exports.rs` is gated `cfg(any(feature = "provider-openai", feature = "provider-llamacpp"))` so it runs in the live suite too.
- **Live llama.cpp**: server-dependent tests probe `GET {base}/models`; an unreachable server prints `SKIP: llama.cpp not reachable: ...` and the test passes, unless `CUCA_REQUIRE_LIVE=1` turns the skip into a panic. `CUCA_BASE_URL` (default `http://127.0.0.1:1234/v1`, not llama-server's own default port 8080) and `CUCA_MODEL` (default: first id the server reports) configure the target. The MCP echo server lives in `plugin_mcp.rs`: the test binary re-executes itself with `--mcp-echo-server` and serves an rmcp stdio echo server before libtest's main (via a `ctor` interceptor).
- **Live local model**: `tests/provider_local.rs` runs one real GGUF model per invocation, on the CPU by default, and needs no server. It loads `CUCA_LOCAL_MODEL_PATH=<file.gguf>` (wins), or downloads into the cache (`CUCA_CACHE_DIR` overrides the cache directory) the model `CUCA_LOCAL_MODEL` names (a preset from `ModelSource::PRESETS`, for example `gemma4-e2b-q4_0`, `qwen3-0.6b-q8_0`, `phi4-mini-q4_0`; or an unverified `repo:revision:file`), or the pinned default (Gemma 4 E2B Q4_0, 2.84 GB) when `CUCA_LOCAL_DOWNLOAD=1`; with none set each test prints `SKIP: local model not available: ...` and passes, unless `CUCA_REQUIRE_LIVE=1` turns the skip into a panic. What runs is derived from the loaded model's own chat template (reasoning present, reasoning switchable through `enable_thinking`, a `tools` variable), not from its name: scenarios that do not apply print `MATRIX|<scenario>|SKIP|<reason>`, and a model limit that was checked against the HuggingFace f32 reference prints `KNOWN-LIMIT` (the `known_limit` table in the test; everything else that fails is a failure). The scenarios are a factual greedy answer with exact usage (prompt tokens equal prefix-reuse read plus write, a `max_tokens` cap is met to the token, and the prompt token count equals the HuggingFace oracle's when `CUCA_LOCAL_REF_DIR` points at `.omp/local-models/ref`-style dumps), thinking on and off, a tool round trip (tools declared on both requests, and again with none on the follow-up), a 1,300-token needle (`PELICAN`) and prefix reuse (warm and cold greedy output must be identical). candle picks its SIMD kernels at compile time, so build for the host CPU: `CUCA_LOCAL_MODEL=qwen3-0.6b-q8_0 RUSTFLAGS="-C target-cpu=native" cargo test --release --features provider-local --test provider_local -- --test-threads=1 --nocapture` (the same `RUSTFLAGS` and `CUCA_LOCAL_MODEL` / `CUCA_LOCAL_MODEL_PATH` apply to `cargo run --release --example local_model --features provider-local`; `CUCA_LOCAL_DRAFTER` (a preset or `in-trunk`) / `CUCA_LOCAL_DRAFTER_PATH` add the MTP drafter there and in `tests/provider_local_mtp.rs`, where `CUCA_LOCAL_DRAFT_TOKENS` may be a comma list). `CUCA_LOCAL_DEVICE` (`LocalDevice` syntax, e.g. `vulkan`; read only by the tests and `examples/local_model.rs`, not by the library) sets `LocalModelConfig::device`, and a GPU device needs its feature: `CUCA_LOCAL_DEVICE=vulkan CUCA_LOCAL_DOWNLOAD=1 cargo test --release --features provider-local-vulkan --test provider_local`, or `CUCA_LOCAL_DEVICE=vulkan cargo run --release --example local_model --features provider-local-vulkan` (it prints `loaded on <device>`). The unit tests `gpu_matches_cpu_on_the_tiny_gemma4`, `gpu_matches_cpu_on_every_architecture`, `gpu_matches_cpu_on_other_weight_dtypes` and `gpu_drafter_matches_cpu_drafter` (`src/provider/local/model/gpu.rs`) compare the GPU engine to a CPU reference on tiny random models; they run only when `CUCA_LOCAL_DEVICE` names a GPU and otherwise print `SKIP: set CUCA_LOCAL_DEVICE to a GPU device` (CI has no GPU): `CUCA_LOCAL_DEVICE=vulkan cargo test --release --no-default-features --features provider-local-vulkan --lib gpu_`. The live matrix was also run on Vulkan (AMD RX 9070 XT, Windows) for Gemma 4 E2B Q4_0, OLMo 2 1B, Granite 3.3 2B and (tiered) Qwen3-30B-A3B, with the same results as the CPU; every other model was run on the CPU, and Metal, CUDA and ROCm are compile-checked only.
- **Tiered experts**: `CUCA_LOCAL_EXPERTS` (`ExpertPlacement` syntax: `resident`, or `tiered:` with comma-separated `ram=`, `device=` (sizes with optional `k`/`m`/`g`) and `threads=`; read only by the tests and `examples/local_model.rs`) sets `LocalModelConfig::experts` in `tests/provider_local.rs`, `tests/provider_local_tiers.rs` and the example. `provider_local_tiers.rs` loads the reference placement (`CUCA_LOCAL_EXPERTS_REF`, default resident), then the tiered one cold, then warm from the exported heat, and asserts identical greedy replies, the byte bounds and that the warm start saves reads while generating; it prints `TIERS|<phase>|<tok/s>|<stats>`. The unit tests `tiered_experts_match_resident_bit_for_bit`, `tiered_load_rejects_a_budget_below_n_used`, `warm_from_loads_the_hottest_experts_first` (`cpu.rs`), the `tier.rs` tests, and `gpu_tiered_experts_match_gpu_resident` plus `gpu_moe_one_row_experts_match_single_tokens` (`gpu.rs`, GPU-gated like the other `gpu_` tests) cover the mechanism. Live tiered runs on the CPU: OLMoE 1B-7B at `tiered:ram=500m` and Qwen3-30B-A3B at `tiered:ram=4g` and `tiered:ram=1100m` (plus the whole matrix at `4g`) reproduce the resident replies. On Vulkan (RX 9070 XT): OLMoE 1B-7B resident against `tiered:device=1g,ram=0`, Qwen3-30B-A3B `tiered:device=2g,ram=0` against `tiered:device=6g,ram=12g` (cold and warm, three models in one process), and the whole matrix for Qwen3-30B-A3B at `device=6g,ram=12g` pass. Two GPU fixes made that work: an expert with one row in a multi-row pass runs the single-token form (a slice, host-scalar weight; the gather plus `[1, 1]` weight-tensor form lost the device once the kernels were tuned), and dropping a `GpuTransformer`/`GpuDrafter` calls `Device::memory_cleanup` (burn's pools kept a dropped model's pages, so the third model ran out of device memory). The `quantized view float vector size ... num_quants` panics printed during autotune come from failing `gemm` candidates (cubek-matmul 0.3 sizes a quantized operand's view in stored words); the tuner discards them.
- **DFlash drafter**: `tests/provider_local_mtp.rs` with `CUCA_LOCAL_MODEL=muse-glimmer-30b-q4_0 CUCA_LOCAL_DRAFTER=meta-models/Muse-Glimmer-30B-assistant:c676cce91658f9568aaf264a416211e2782735b7` (a checkpoint source, converted at `CUCA_LOCAL_CONVERT_QUANT`; or `CUCA_LOCAL_DRAFTER=<repo>:<rev>:dflash-Muse-Glimmer-30B-Q4_0.gguf`, llama.cpp's file) and `CUCA_LOCAL_DRAFT_TOKENS=5,7,15` runs the block drafter (CPU only, one request at a time). Unit tests in `model/cpu/dflash.rs` and `engine/mod.rs` (`dflash_*`) cover the block against a plain-loop reference, the context ring, greedy equality with plain decoding, warm prefix reuse and failed-request recovery; `convert/dflash.rs` tests the converter; `convert/oracle_dflash.rs` compares with transformers on tiny checkpoints written by `.omp/local-models/dflash/make_tiny_dflash.py` when `CUCA_LOCAL_DFLASH_REF=<dir>` is set (`--rows 6` for a short block, `--neg convention|embednorm|window` for negative controls that must fail).
- **Checkpoint conversion**: `ModelSource::Checkpoint { repo, revision }` (`"repo:revision".parse()`) and `ModelSource::Dir(path)` convert a Hugging Face safetensors checkpoint to a cached GGUF (`src/provider/local/convert/`, a pure-Rust port of llama.cpp's `convert_hf_to_gguf.py` at commit `67107ac34f62882d8b53ea41ad68010ea635b9be`, streamed tensor by tensor, `LocalModelConfig::convert.quant` = `f16` / `q8_0` default / `q4_0`, output `<cache>/converted/.../model-<quant>.gguf`). `CUCA_LOCAL_CONVERT_QUANT` sets the precision in `tests/provider_local.rs`, `provider_local_mtp.rs`, `provider_local_tiers.rs` and the example; `CUCA_LOCAL_MODEL_PATH` naming a directory selects `ModelSource::Dir`, `CUCA_LOCAL_MODEL=repo:revision` a `Checkpoint`, and the live matrix reports a checkpoint under its preset's name (`CHECKPOINT_PRESETS`) so the known limits apply. `tests/provider_local_convert.rs` (and the unit test `convert::oracle`, same `CUCA_LOCAL_REF_DIR` gate, `CUCA_LOCAL_CONVERT_ONLY=<repo substring>`) check F16 conversions against the transformers oracle. The converter was verified by running the real script on the same checkpoints and diffing the GGUFs (dev scripts in `.omp/local-models/convert/`, gitignored). Split GGUF files (`<base>-00001-of-0000N.gguf`, from a `ModelSource::File` naming any part or a Hugging Face split name) are merged into one cached GGUF by `convert/gguf_merge.rs` (streaming, through the converter's `.partial`/`.lock` pattern); a Hugging Face merge deletes the downloaded parts.
- **Continuous batching**: the local engine is a step scheduler (`src/provider/local/engine/scheduler.rs`): up to `LocalModelConfig::batching.max_sequences` (default 4) requests share one forward pass per step (`Model::forward_batch`: dense layers over all rows, attention and a hybrid model's recurrent scan per sequence) over one shared K/V pool (`kv_tokens`, default twice `context_length`: the memory knob, independent of `max_sequences`), with prefill chunks next to the decode rows, preemption of the youngest sequence when the pool is full, and `LocalModel::serving_stats`. A hybrid model resumes a prefix from a recurrent-state snapshot taken at a block boundary (`Model::snapshot`/`restore`). `CUCA_LOCAL_BATCHING` (`BatchingConfig` syntax, `seqs=4,kv=16384,step=256,prefix=off`; read by `examples/local_model.rs` and `tests/provider_local_batch.rs`) sets it. `provider_local_batch.rs` prints `BATCH|<scenario>|...` lines (steps and rows, equality with the serial replies, prefix hits, aggregate tokens per second for 1 and 4 sequences); on the CPU a batched reply must equal the serial one bit for bit, on a GPU it agrees only up to float rounding. CPU unit tests: `batched_rows_equal_solo_rows_for_every_architecture`, `batched_equals_solo_for_every_architecture` and the scheduler tests in `engine/scheduler.rs`; GPU: `gpu_batched_matches_gpu_solo_on_every_architecture` (part of the `model::gpu` ladder).
- **Tensor parallelism**: `LocalModelConfig::shards` (GPU only; `LocalModelConfig::set_devices("vulkan:0+vulkan:1")` fills `device` and `shards` from a `+`-separated list, which is what `CUCA_LOCAL_DEVICE` carries in `tests/provider_local.rs`, `provider_local_batch.rs` and `examples/local_model.rs`, whose `loaded on` line lists the devices) splits a model over `1 + shards.len()` devices: `src/provider/local/model/tp.rs` (rules, which heads/rows/columns a shard owns, the all-reduce) and `gpu.rs` (per-shard `Weights`, K/V pools and passes; `Weights::layer` = mixer, all-reduce, attention tail, FFN half, all-reduce, FFN tail). A device may repeat (`vulkan:0+vulkan:0` runs the path on one GPU, no speedup). Models with fewer K/V heads than devices replicate them; MoE experts are sliced inside every expert; delta-net layers, full-width Q/K norms, a drafter and tiered experts are rejected with `tensor parallelism: ...`. The all-reduce is NCCL on CUDA (Linux, distinct devices, compile-checked only) and host-staged in shard order elsewhere, so runs are deterministic. GPU unit tests: `gpu_sharded_matches_single_device`, `gpu_sharded_rejects_unsplittable_heads`, `gpu_all_reduce_adds_in_shard_order` (run with `CUCA_LOCAL_DEVICE=vulkan:0+vulkan:0`); the live matrix with the same device string must give the single-device replies.
- **Paged K/V and test knobs**: the local engine keeps K/V in blocks of 16 positions named by token ids (`src/provider/local/model/paged.rs`; block pools, per-sequence block tables, a prefix store), so `read_tokens` is a multiple of 16. `CUCA_LOCAL_PRINT_REPLIES=1` makes `tests/provider_local.rs`, `provider_local_tiers.rs` and `provider_local_mtp.rs` print every greedy reply as a `REPLY|...` line (the diff of a before/after run is the regression check for attention or K/V changes; tool-call ids are random, mask them); `CUCA_LOCAL_PERF=1` enables `perf_long_prompt` in `provider_local.rs` (a 1,100-token prompt, 3 rounds, prints `PERF|model|round|prompt|cached|completion|first|decode tok/s`; run it on a worktree of the previous commit with the same `CARGO_TARGET_DIR` rules to A/B decode and prefill). Unit tests: `paged_attention_matches_contiguous_attention`, `a_row_is_bit_identical_alone_and_in_a_batch`, `sliding_blocks_released_behind_the_window_change_nothing`, `prefix_store_evicts_lru_unreferenced_blocks_only`, `two_prompts_sharing_a_prefix_hit_in_blocks`, `sliding_group_releases_old_blocks` and, GPU-gated like every `gpu_` test, `gpu_paged_decode_kernel_matches_cpu` and `gpu_prefill_gather_matches_decode_rows`; run the whole GPU ladder with `--lib model::gpu` (the `gpu_` filter skips several GPU-gated tests).
- **Run**: `cargo test --features provider-llamacpp` for unit tests; the live command in Development Commands for the integration suite.
